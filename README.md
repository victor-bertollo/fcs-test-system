# FCS Test System

FCS Test System автоматически проверяет цифровые микросхемы и схемы,
собранные на breadboard. Компьютер передаёт тестовые наборы на ESP32-C3,
ESP управляет линиями через MCP23017, считывает ответ проверяемого устройства,
а Python сравнивает его с YAML-тестом.

В проекте есть две платформы:

- **тестер микросхем** — для DIP14 и DIP16 серии 74HC;
- **тестер макеток** — с 32 динамически настраиваемыми сигнальными каналами.

Подробное устройство системы и правила создания тестов описаны в
[технической документации](dev/documentation/documentation.md).

## Установка

Понадобятся:

- Windows, macOS или Linux;
- Git;
- Python 3.10 или новее;
- USB-кабель с передачей данных;
- одна из проверочных платформ.

Скачайте проект:

```bash
git clone https://github.com/victor-bertollo/fcs-test-system.git
cd fcs-test-system
```

Все следующие команды выполняются из каталога `fcs-test-system`.

### Windows PowerShell

Создайте виртуальное окружение:

```powershell
py -3 -m venv .venv
```

Если PowerShell запрещает запуск `Activate.ps1`, один раз разрешите локальные
подписанные сценарии для текущего пользователя:

```powershell
Set-ExecutionPolicy RemoteSigned -Scope CurrentUser
```

Команда не изменяет политику для всей системы. PowerShell может попросить
подтверждение. Затем активируйте окружение и установите зависимости:

```powershell
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

### macOS и Linux

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

При следующих запусках достаточно перейти в каталог проекта и снова
активировать `.venv`.

## Подключение платформы к компьютеру

1. Подключите USB-кабель к ESP32 на платформе.
2. Подключите кабель к компьютеру и подождите несколько секунд.
3. Определите появившийся последовательный порт.

Кабель только для зарядки не подойдёт.

### Windows

Откройте **Диспетчер устройств → Порты (COM и LPT)**. Порт обычно называется
`COM3`, `COM4` и т. п. Если определить его трудно, сравните список до и после
подключения ESP.

Для наиболее стабильного отображения цветных таблиц рекомендуется Windows
Terminal. Если терминал некорректно показывает цвета, запустите тест макетки с
`--no-color`.

### macOS

```bash
ls /dev/cu.*
```

Порт обычно выглядит как `/dev/cu.usbmodem...` или
`/dev/cu.usbserial-...`.

### Linux

```bash
ls /dev/ttyACM* /dev/ttyUSB*
```

При ошибке `Permission denied` добавьте пользователя в группу `dialout`, затем
выйдите из системы и войдите снова:

```bash
sudo usermod -aG dialout "$USER"
```

## Проверка отдельной микросхемы

### Как вставлять DIP16 и DIP14

Перед установкой или извлечением чипа всегда отключайте USB-питание.

Найдите ключ на корпусе — полукруглую выемку или точку около вывода 1 — и
совместите его с ключом на слоте платформы.

- **DIP16** имеет по восемь ножек с каждой стороны и занимает все 16 контактов
  слота: вывод чипа N соответствует каналу N.
- **DIP14** имеет по семь ножек с каждой стороны. Его нужно выровнять по стороне
  ключа и вывода 1. Контакты слота 8 и 9 останутся пустыми.

Соответствие DIP14:

| Вывод чипа | Канал слота |
| ---: | ---: |
| 1–7 | 1–7 |
| — | 8–9 не используются |
| 8–14 | 10–16 |

Поэтому у DIP14 земля на выводе 7 попадает на канал 7, а VCC на выводе 14 —
на канал 16. Не сдвигайте DIP14 к нижнему краю слота: это изменит соответствие
пинов и может подать питание не туда.

Убедитесь, что все ножки вошли в контакты и не загнулись, и только после этого
подключайте USB.

### Готовые тесты чипов

| YAML | Микросхема | Назначение |
| --- | --- | --- |
| `not.yaml` | 74HC04 | NOT |
| `and.yaml` | 74HC08 | AND |
| `or.yaml` | 74HC32 | OR |
| `xor.yaml` | 74HC86 | XOR |
| `add.yaml` | 74HC283 | 4-битный сумматор |
| `demux.yaml` | 74HC139 | дешифратор/демультиплексор |
| `mux.yaml` | 74HC157 | мультиплексор |
| `cnt.yaml` | 74HC161 | 4-битный счётчик |

Выбирайте YAML по маркировке чипа. Примеры запуска:

```powershell
# Windows
python chip_tester/chip_tester.py chip_tester/configs/not.yaml --port COM3
```

```bash
# macOS
python chip_tester/chip_tester.py chip_tester/configs/not.yaml --port /dev/cu.usbmodem1101

# Linux
python chip_tester/chip_tester.py chip_tester/configs/not.yaml --port /dev/ttyACM0
```

Чтобы печатать каждый успешно выполненный набор, добавьте `--show-passes`.

## Проверка собранной макетки

### 34 контакта и пять штекеров

От платформы к макетке выведены 34 активных контакта:

1. физический контакт 1 — **GND**;
2. физический контакт 2 — **VDD 3,3 В**;
3. следующие 32 контакта — динамические сигнальные каналы 1–32.

Они распределены по 8-контактным штекерам так:

| Штекер | Содержимое по порядку |
| ---: | --- |
| 1 | GND, VDD, каналы 1–6 |
| 2 | каналы 7–14 |
| 3 | каналы 15–16, затем шесть пустых мест |
| 4 | каналы 17–24 |
| 5 | каналы 25–32 |

В отличие от старой платформы, здесь нет отдельных постоянных групп `DRIVER`
и `RECEIVER`. Каждый из каналов 1–32 становится управляющим входом, тактовым
сигналом, считываемым выходом или отключённой линией согласно `pins_type` в
выбранном YAML.

Питание макетки подключайте только через выделенные GND и VDD. Символы `g` и
`v` в `pins_type` задают логические уровни на сигнальном MCP-пине и не заменяют
силовое питание макетки.

### Безопасное подключение

1. Отключите платформу от USB.
2. Выберите YAML и прочитайте `pins_type`, `input_labels` и `output_labels`.
3. Подключите GND и VDD к шинам питания проверяемой макетки.
4. Подключите каналы с типом `i` или `c` только ко входам схемы.
5. Подключите каналы с типом `o` только к выходам схемы.
6. Неиспользуемые каналы оставьте неподключёнными.
7. Проверьте порядок старших и младших битов, затем подключите USB.

> Не соединяйте канал, настроенный как `i`, `c`, `g` или `v`, с выходом
> проверяемой схемы. Два выхода могут установить разные уровни и повредить
> оборудование.

Динамические каналы программно разделены на блоки 1–8, 9–16, 17–24 и 25–32.
Внутри одного блока нельзя смешивать управляющие `i/c` и считываемые `o`.
Граница этих логических блоков не совпадает с границами первых трёх физических
штекеров.

### Готовые тесты макеток

| YAML | Назначение |
| --- | --- |
| `adder_4bit_with_carry.yaml` | 4-битный сумматор с переносом |
| `multiplier_4x4.yaml` | 4-битный беззнаковый умножитель |
| `divider_4bit.yaml` | 4-битное деление с остатком |
| `and_1bit.yaml` | однобитный AND |
| `mux_1bit.yaml` | однобитный мультиплексор |
| `first_8_pins_sweep.yaml` | диагностический перебор первых восьми входов |

Перед подключением ориентируйтесь на смысловые имена в конкретном YAML.
Например, у умножителя входы идут как `A3…A0, B3…B0`, а выходы — как
`P7…P0`.

### Запуск теста макетки

```powershell
# Windows
python maket_tester/tester.py maket_tester/configs/multiplier_4x4.yaml --port COM3
```

```bash
# macOS
python maket_tester/tester.py maket_tester/configs/multiplier_4x4.yaml --port /dev/cu.usbmodem1101

# Linux
python maket_tester/tester.py maket_tester/configs/multiplier_4x4.yaml --port /dev/ttyACM0
```

Можно передать несколько YAML или glob-шаблон:

```bash
python maket_tester/tester.py "maket_tester/configs/*.yaml" --port /dev/ttyACM0
```

Диагностический sweep печатает значения выходов, но не сравнивает их:

```bash
python maket_tester/tester.py maket_tester/configs/first_8_pins_sweep.yaml \
  --port /dev/ttyACM0 --show-passes
```

## Как понимать результат макетного тестера

Без `--show-passes` программа показывает живую панель со счётчиком
`Passed tests: k/total` и таблицами последнего пройденного набора. С
`--show-passes` каждая таблица сохраняется в терминале.

При ошибке выводится таблица входов и выходов. Правильные значения зелёные,
неправильные красные, а `SKIP` означает, что значение не проверялось. После
таблицы перечисляются смысловое имя сигнала, адрес MCP, физический канал,
ожидаемое и полученное значения.

Пример фрагмента:

```text
FAIL 0003: 0 + 2 + 0 = 2
  INPUT:
│PIN     │ Cin │  A3 │  A2 │  A1 │  A0 │  B3 │  B2 │  B1 │  B0 │
│VALUE   │  0  │  0  │  0  │  0  │  0  │  0  │  0  │  1  │  0  │
  OUTPUT:
│PIN     │ Cout│  S3 │  S2 │  S1 │  S0 │
│EXPECTED│  0  │  0  │  0  │  1  │  0  │
│RECEIVED│  0  │  0  │  0  │  0  │  0  │
│RESULT  │  OK │  OK │  OK │ FAIL│  OK │
  ERRORS:
    S1 (MCP 0x21 pin 4): expected 1, received 0
```

## Параметры командной строки

Полная справка:

```bash
python chip_tester/chip_tester.py --help
python maket_tester/tester.py --help
```

| Параметр | Чип | Макетка | Назначение |
| --- | :---: | :---: | --- |
| `--port` | да | да | последовательный порт ESP |
| `--baud` | да | да | скорость Serial, обычно 115200 |
| `--timeout` | да | да | время ожидания ответа |
| `--show-passes` | да | да | печатать каждый успешный тест |
| `--raw` | да | да | показывать низкоуровневый обмен |
| `--no-color` | нет | да | отключить ANSI-цвета |
| `--stop-on-fail` | нет | да | остановиться после первого FAIL, игнорируя YAML |
| `--not-stop-on-fail` | нет | да | выполнить все наборы, игнорируя YAML |

Параметры `--stop-on-fail` и `--not-stop-on-fail` взаимно исключают друг друга.
Если ни один не указан, используется `stop_on_fail` из YAML.

## Кратко о YAML макетки

```yaml
board: example
stop_on_fail: true
pins_type: "iiiiiiiizzzzzzzzoooooooozzzzzzzz"
input_labels: [A3, A2, A1, A0, B3, B2, B1, B0]
output_labels: [Y7, Y6, Y5, Y4, Y3, Y2, Y1, Y0]

tests:
  - name: example vector
    input: "00010010"
    expected: "00000010"
```

`pins_type` описывает все 32 динамических канала, а `input` и `expected`
содержат только компактные значения для каналов `i` и `o`. Подробный контракт
и инструкция по созданию теста находятся в
[технической документации](dev/documentation/documentation.md).

## Частые проблемы

### Не найден `serial` или `yaml`

Активируйте `.venv` и выполните:

```bash
python -m pip install -r requirements.txt
```

### Порт не найден или занят

- проверьте USB-кабель и имя порта;
- закройте Arduino Serial Monitor и другие программы, использующие порт;
- переподключите ESP и снова найдите порт;
- на Linux проверьте членство в группе `dialout`.

### Платформа не отвечает

- убедитесь, что загружена прошивка от нужной платформы;
- попробуйте `--raw`;
- увеличьте `--timeout`;
- проверьте I²C-подключение и адреса MCP23017.

### Тест падает на разных наборах

- проверьте общий GND и стабильное питание 3,3 В;
- не используйте сигнальный MCP-пин вместо выделенного VDD;
- проверьте контакты штекеров и breadboard-проводов;
- убедитесь, что вход и выход не смешаны внутри одного 8-канального блока;
- сравните порядок сигналов с `input_labels` и `output_labels`.

После любого `FAIL` сначала отключите USB и только затем меняйте подключение.
